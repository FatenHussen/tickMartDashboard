# Display Defaults — لغة وعملة العرض الافتراضية

المطلوب: في الداشبورد خياران — **لغة العرض الافتراضية** و**عملة العرض الافتراضية** — تُطبَّق على التطبيق والويب، ويبقى المستخدم قادرًا على اختيار ما يناسبه بعدها.

الواجهة في الداشبورد **جاهزة** (تبويب «إعدادات العرض الافتراضية» داخل الإعدادات). هذا الملف يشرح ما ينقص من الباك.

---

## 1) المبدأ

القيمتان **إعداد عرض فقط**. لا تغيّران البيانات المخزّنة:

- الأسعار تبقى مخزّنة بالعملة الأساسية (`base currency`)، والتحويل عند العرض فقط عبر `exchange_rate`.
- كل الترجمات تبقى متاحة في قاعدة البيانات، والافتراضي يحدّد فقط أيّها يُعرض أولًا.

**ترتيب الأولوية عند تحديد ما يراه المستخدم** (من الأعلى للأدنى):

1. اختيار المستخدم المحفوظ (في حسابه إن كان مسجّلًا، أو في تخزين الجهاز إن كان زائرًا).
2. `Accept-Language` / عملة مرسلة في رأس الطلب — اختياري.
3. **القيمة الافتراضية من هذه الإعدادات.**
4. قيمة ثابتة في التطبيق كحل أخير (`ar` / العملة الأساسية).

> اختيار المستخدم دائمًا له الأولوية. تغيير الافتراضي **لا** يعيد ضبط اختيارات المستخدمين الحاليين.

---

## 2) مفتاحا الإعداد

يُضافان إلى جدول `system_settings` ضمن مجموعة جديدة اسمها `localization`:

| key | type | value | مثال |
|---|---|---|---|
| `default_display_language` | `string` | كود لغة موجود في جدول `languages` | `ar` |
| `default_display_currency` | `string` | كود عملة موجود في جدول `currencies` | `SAR` |

ملاحظات:

- القيمة **كود** (`code`) وليست `id` — الكود مستقر وأوضح للتطبيق.
- يجب أن يكون السجل المقابل `is_active = true`، وإلا تُرفض القيمة.
- لازم `seeder` يضبط المفتاحين على اللغة/العملة التي `is_default = true` حاليًا، حتى لا يبدآ فارغين.

---

## 3) Endpoints المطلوبة

### 3.1 قراءة المجموعة (أدمن) — موجود غالبًا

```
GET /api/admin/system-settings/group/localization
```

يكفي أن يُرجع المفتاحين بنفس شكل مجموعة `delivery` الحالية:

```json
{
  "status": true,
  "message": "ok",
  "data": [
    { "key": "default_display_language", "value": "ar", "type": "string" },
    { "key": "default_display_currency", "value": "SAR", "type": "string" }
  ]
}
```

الداشبورد يقرأ أي شكل من هذه الأشكال (مصفوفة، أو كائن `key: value`، أو `data.items`).

### 3.2 التحديث (أدمن) — موجود

```
PUT /api/admin/system-settings/{key}
Body: { "value": "ar" }
```

الداشبورد يرسل نداءً لكل مفتاح تغيّر. **المطلوب إضافته: التحقق (validation).**

**قواعد التحقق:**

| الحالة | الرد |
|---|---|
| `default_display_language` لا يطابق أي `languages.code` | `422` — «اللغة غير موجودة» |
| اللغة موجودة لكن `is_active = false` | `422` — «اللغة غير مفعّلة» |
| `default_display_currency` لا يطابق أي `currencies.code` | `422` — «العملة غير موجودة» |
| العملة موجودة لكن `is_active = false` | `422` — «العملة غير مفعّلة» |

**الصلاحية:** `setting.update` (نفس صلاحية بقية الإعدادات).

### 3.3 القراءة العامة (التطبيق والويب) — **مطلوب جديد**

هذا هو الجزء الناقص فعليًا. يحتاج التطبيق والويب نداءً **بدون مصادقة** يقرأ منه القيمتين عند الإقلاع:

```
GET /api/settings/display-defaults
```

```json
{
  "status": true,
  "message": "ok",
  "data": {
    "language": {
      "code": "ar",
      "native_name": "العربية",
      "direction": "rtl",
      "flag_icon": "https://…/flags/sa.png"
    },
    "currency": {
      "code": "SAR",
      "name": { "ar": "ريال سعودي", "en": "Saudi Riyal" },
      "symbol": "ر.س",
      "exchange_rate": 1
    },
    "available_languages": [
      { "code": "ar", "native_name": "العربية", "direction": "rtl", "flag_icon": "…" },
      { "code": "en", "native_name": "English", "direction": "ltr", "flag_icon": "…" }
    ],
    "available_currencies": [
      { "code": "SAR", "name": { "ar": "ريال سعودي", "en": "Saudi Riyal" }, "symbol": "ر.س", "exchange_rate": 1 }
    ]
  }
}
```

**لماذا كائن كامل وليس كودًا فقط:** حتى يرسم التطبيق شاشة الإقلاع (الاتجاه `rtl/ltr`، رمز العملة، قائمة الخيارات) من نداء واحد، دون نداءين إضافيين للغات والعملات.

**مهم:** `available_languages` و`available_currencies` تُرجع المفعّل فقط (`is_active = true`) — هذه هي القائمة التي يختار منها المستخدم لاحقًا.

**التخزين المؤقت (Cache):** القيم نادرة التغيّر. يُفضّل `cache` على مستوى الخادم مع إبطاله عند تحديث أي من المفتاحين أو عند تعديل جدول `languages` / `currencies`. وضع `ETag` أو `Cache-Control: public, max-age=300` يخفّف الحمل عند الإقلاع.

## 4) تطبيق الافتراضي على بقية الـ APIs

بعد قراءة الافتراضي، يرسل التطبيق تفضيل المستخدم في كل طلب:

```
Accept-Language: en
X-Currency: USD
```

على الباك، `middleware` يحسم اللغة والعملة لكل طلب حسب ترتيب الأولوية في القسم (1):

- **اللغة:** تضبط `app()->setLocale()`، فتُرجع الحقول المترجمة باللغة الصحيحة.
- **العملة:** تضبط عملة العرض، فتُحوَّل الحقول المالية في الـ `Resources` وتُرجع مع `*_formatted` بالرمز الصحيح.

إن لم يُرسل التطبيق شيئًا، يقع الـ `middleware` على القيمة الافتراضية من الإعدادات.

---

## 5) العلاقة بـ `is_default` الموجود

جدولا `languages` و`currencies` فيهما `is_default` أصلًا. لتفادي مصدرَي حقيقة متعارضين، اختر أحد المسارين:

**المسار (أ) — المفتاحان هما المصدر (الموصى به):**
عند حفظ `default_display_language` / `default_display_currency`، يُحدَّث `is_default` في الجدول المقابل ضمن نفس الـ transaction (يُرفع عن السجل الجديد ويُنزع عن القديم). يبقى `is_default` صحيحًا لأي كود قديم يعتمد عليه.

**المسار (ب) — الجدول هو المصدر:**
تُلغى فكرة المفتاحين، وتُضاف بدلًا منهما نقطتان:
`PUT /api/admin/languages/{id}/set-default` و`PUT /api/admin/currencies/{id}/set-default`.

> الداشبورد الآن يعمل على المسار (أ)، ويقرأ `is_default` كقيمة احتياطية إن لم يوجد المفتاحان بعد — أي أن التبويب يعرض الصحيح حتى قبل إضافة المفتاحين. لو اخترتم المسار (ب) أخبروني لأبدّل الاستدعاءات.

---

## 6) الملخّص — ما المطلوب من الباك

1. إضافة المفتاحين `default_display_language` و`default_display_currency` إلى `system_settings` ضمن مجموعة `localization`، مع `seeder` يملأهما من `is_default` الحالي.
2. دعم `GET /api/admin/system-settings/group/localization`.
3. إضافة **التحقق** على `PUT /api/admin/system-settings/{key}` للمفتاحين (موجود؟ مفعّل؟) مع رسائل `422` واضحة.
4. مزامنة `is_default` في جدولي `languages` و`currencies` عند الحفظ (المسار أ).
5. **إضافة `GET /api/settings/display-defaults` العام** — بدون مصادقة، يُرجع الافتراضي + القوائم المفعّلة، مع `cache`.
6. `middleware` يحسم اللغة والعملة لكل طلب حسب الأولوية: اختيار المستخدم ← رؤوس الطلب ← الافتراضي.

النقطة (5) هي الأساسية: بدونها لا يستطيع التطبيق ولا الويب قراءة الافتراضي أصلًا.
